# auth Specification

## Purpose
이메일과 비밀번호로 계정을 만들고 JWT 로 로그인 상태를 유지하며, 본인의 이름과 비밀번호를 고치는 인증 기능이다. 로그인하지 않으면 뒤의 모든 화면이 막힌다.

## Requirements

### Requirement: 회원가입
<!-- 근거: B-05 · B-06 · B-07 · B-08 · B-09 · B-10 / login.html -->
시스템은 이메일 · 비밀번호 · 이름으로 계정을 만들고 JWT 를 돌려줘야 한다(SHALL). 이메일은 유일해야 하며 비밀번호는 8자 이상이어야 한다. 비밀번호는 bcrypt 해시로만 저장한다(MUST). 응답은 201 이다.

#### Scenario: 가입 성공
- **WHEN** 올바른 이메일, 8자 이상 비밀번호, 이름으로 `POST /api/auth/signup` 을 부른다
- **THEN** 201 과 JWT 를 돌려주고 계정이 만들어진다

#### Scenario: 이메일 형식 오류
- **WHEN** 형식이 틀린 이메일로 가입을 요청한다
- **THEN** 400 `EMAIL_INVALID` 를 돌려주고 화면은 이메일 칸 아래에 "이메일 형식이 올바르지 않음" 을 보인다

#### Scenario: 이메일 중복
- **WHEN** 이미 가입된 이메일로 가입을 요청한다
- **THEN** 409 `EMAIL_DUPLICATED` 를 돌려주고 화면은 폼 위쪽 오류 상자에 "이미 가입된 이메일" 을 보인다

#### Scenario: 약한 비밀번호
- **WHEN** 8자 미만 비밀번호로 가입을 요청한다
- **THEN** 400 `PASSWORD_TOO_WEAK` 를 돌려주고 화면은 비밀번호 칸 아래에 "비밀번호는 8자 이상" 을 보인다

### Requirement: 가입 화면의 입력과 처리 중 상태
<!-- 근거: B-05 · B-06 · B-07 / login.html -->
가입 화면은 이름 칸과 초대코드 칸(선택)을 회원가입 상태에서만 보여야 한다(SHALL). 제출 전에는 오류를 띄우지 않고, 요청이 나간 동안에는 제출 버튼을 잠가 두 번 눌리지 않게 해야 한다(MUST).

#### Scenario: 가입 초기 상태
- **WHEN** 사용자가 로그인 화면에서 "회원가입" 을 누른다
- **THEN** 이름 칸과 초대코드 칸이 나타나고, 제목은 "회원가입", 버튼은 "가입하기" 가 된다

#### Scenario: 입력 중에는 오류를 띄우지 않음
- **WHEN** 사용자가 칸을 채우는 중이고 아직 제출하지 않았다
- **THEN** 어떤 오류 문구도 보이지 않는다

#### Scenario: 처리 중
- **WHEN** 가입 요청을 보낸 뒤 응답을 기다린다
- **THEN** 버튼은 "처리 중..." 으로 바뀌고 비활성이 된다

### Requirement: 초대코드 입력과 팀 합류 분기
<!-- 근거: B-05 · B-11 / login.html, team.html -->
초대코드를 넣고 가입하면 가입 직후 합류를 요청해야 한다(SHALL). 합류가 실패해도 가입 계정은 유지하며, 초대코드를 비우면 가입만 하고 팀 생성은 팀 화면의 onboard 상태에서 한다.

#### Scenario: 초대코드 없이 가입
- **WHEN** 초대코드를 비우고 가입에 성공한다
- **THEN** 사용자는 `team.html` 의 "아직 소속 팀이 없음" 상태로 이동한다

#### Scenario: 없는 초대코드
- **WHEN** 존재하지 않는 초대코드로 가입하고 합류를 요청한다
- **THEN** 계정은 그대로 남고, 합류는 404 `INVITE_NOT_FOUND` 이며, 사용자는 팀 화면으로 이동해 "없는 초대코드" 를 본다

### Requirement: 로그인
<!-- 근거: B-01 · B-02 · B-04 / login.html -->
시스템은 이메일과 비밀번호가 맞으면 JWT 를 돌려줘야 한다(SHALL). 토큰의 유효 시간은 24시간이며 갱신하지 않는다(MUST). 실패 사유는 이메일 존재 여부를 드러내지 않고 하나의 메시지로 통일한다.

#### Scenario: 로그인 성공
- **WHEN** 맞는 이메일과 비밀번호로 `POST /api/auth/login` 을 부른다
- **THEN** 200 과 JWT 를 돌려주고, 화면은 토큰을 `localStorage` 에 저장한 뒤 소속 팀이 있으면 `meetings.html` 로, 없으면 `team.html` 로 이동한다

#### Scenario: 로그인 실패
- **WHEN** 존재하지 않는 이메일이거나 비밀번호가 틀리다
- **THEN** 어느 쪽이든 401 `INVALID_CREDENTIALS` 를 돌려주고 화면은 "이메일 또는 비밀번호가 올바르지 않음" 을 보인다

### Requirement: 토큰 만료 처리
<!-- 근거: B-03 · H-01 / login.html -->
24시간이 지난 토큰으로 API 를 부르면 시스템은 401 `TOKEN_EXPIRED` 를 돌려줘야 한다(SHALL). 화면은 저장한 토큰을 지우고 로그인 화면으로 보내며, 이메일 칸은 채운 채 비밀번호 칸에 초점을 둔다.

#### Scenario: 세션 만료
- **WHEN** 만료된 토큰으로 어떤 보호된 API 를 부른다
- **THEN** 401 `TOKEN_EXPIRED` 를 받고, 토큰이 지워지고, `login.html` 에서 만료 안내가 보인다

### Requirement: 로그아웃
<!-- 근거: J-01 / profile.html -->
JWT 는 무상태이므로 서버는 블랙리스트를 두지 않아야 한다(MUST NOT). 로그아웃은 화면이 토큰을 지우는 것이고 서버는 200 만 돌려준다.

#### Scenario: 로그아웃
- **WHEN** 사용자가 "로그아웃" 을 누른다
- **THEN** `POST /api/auth/logout` 이 200 을 돌려주고 화면은 토큰을 지운 뒤 `login.html` 로 이동한다

### Requirement: 내 정보 조회
<!-- 근거: J-01 / profile.html -->
`GET /api/auth/me` 는 id · name · email 과 소속 팀의 team_id · 팀 이름 · role 을 돌려줘야 한다(SHALL). 소속 팀이 없으면 세 값은 비어 있다. 이메일은 고칠 수 없다. 로그인 · 가입 응답에도 team_id 가 있다.

#### Scenario: owner 의 내 정보
- **WHEN** 팀의 owner 가 내 정보를 연다
- **THEN** 이름 · 이메일 · "owner" 배지가 보이고 이메일 칸은 입력칸이 아니다

### Requirement: 이름 변경
<!-- 근거: J-02 · J-06 / profile.html -->
`PUT /api/auth/me` 에 이름만 보내면 비밀번호는 그대로 둬야 한다(SHALL). 계정 변경은 팀 활동이 아니므로 활동 기록에 남기지 않는다.

#### Scenario: 이름만 저장
- **WHEN** 이름만 고치고 저장한다
- **THEN** 200 을 받고 화면 머리의 이름이 바뀌며 활동 기록에는 새 줄이 생기지 않는다

### Requirement: 비밀번호 변경
<!-- 근거: J-03 · J-04 · J-05 · J-06 / profile.html -->
비밀번호를 바꾸려면 현재 비밀번호를 함께 받아야 한다(MUST). 현재 비밀번호가 틀리면 401 `UNAUTHORIZED` 를 돌려주고, 새 비밀번호는 8자 이상이어야 한다. 새 비밀번호와 확인 칸이 다르면 화면이 먼저 막고 서버로 보내지 않는다.

#### Scenario: 확인 칸 불일치
- **WHEN** 새 비밀번호와 "한 번 더" 칸이 다르다
- **THEN** 화면은 "두 비밀번호가 다름" 을 보이고 요청을 보내지 않는다

#### Scenario: 현재 비밀번호 틀림
- **WHEN** 현재 비밀번호가 틀린 채로 새 비밀번호를 저장한다
- **THEN** 401 `UNAUTHORIZED` 를 받고 비밀번호는 바뀌지 않는다

#### Scenario: 약한 새 비밀번호
- **WHEN** 8자 미만 새 비밀번호를 저장한다
- **THEN** 400 `PASSWORD_TOO_WEAK` 를 받고 화면은 "비밀번호는 8자 이상" 을 보인다

#### Scenario: 저장 중과 완료
- **WHEN** 저장을 누르고 응답을 기다린다
- **THEN** 버튼은 "저장 중..." 이 되며 비활성이고, 성공하면 200 과 함께 "저장함" 알림이 보인다
