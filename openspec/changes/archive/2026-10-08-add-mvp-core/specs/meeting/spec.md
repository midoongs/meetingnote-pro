# Spec Delta

## Purpose

녹취 파일을 받아쓴 본문을 요약 · 결정사항 · 할 일 세 항목으로 나누어 회의록으로 저장하고, 팀이 목록 · 검색 · 상세로 읽고 고칠 수 있게 하는 기능이다.

## ADDED Requirements

### Requirement: 녹취 업로드와 받아쓰기
<!-- 근거: C-05 · C-06 · C-07 · C-08 · C-09 / meetings.html -->
시스템은 mp3 또는 wav 녹취를 받아 본문 텍스트만 돌려줘야 한다(SHALL). 파일은 4.5MB 이하이며 받아쓰기는 60초 이내에 끝나야 한다. 이 단계에서는 회의록을 저장하지 않는다.

#### Scenario: 받아쓰기 성공
- **WHEN** 4.2MB wav 를 `POST /api/upload` 로 올린다
- **THEN** 200 과 본문 텍스트를 받고 본문 칸이 채워지며 "받아쓰기 완료" 가 보인다. 저장은 아직 되지 않는다

#### Scenario: 올리는 중
- **WHEN** 업로드가 진행 중이다
- **THEN** 파일 이름 · 크기 · 진행 막대와 "받아쓰는 중 62%" 같은 진행률이 보인다

#### Scenario: 형식 오류
- **WHEN** 확장자와 상관없이 내용 형식이 mp3 · wav 가 아니다
- **THEN** 415 `UNSUPPORTED_MEDIA_TYPE` 를 받고 "mp3 또는 wav 만 올릴 수 있음" 알림이 보인다

#### Scenario: 용량 초과
- **WHEN** 4.5MB 를 넘는 파일을 올린다
- **THEN** 413 `PAYLOAD_TOO_LARGE` 를 받고 "4.5MB 를 넘는 파일" 알림이 보이며 분할 업로드는 지원하지 않는다

### Requirement: 회의록 저장과 세 항목 구분
<!-- 근거: C-05 · C-10 · C-11 / meetings.html -->
회의록은 제목 · 회의 시각 · 본문이 필수이다(MUST). 저장할 때 시스템은 본문을 요약 · 결정사항 · 할 일로 나눠 함께 저장해야 한다(SHALL). 저장이 끝나면 입력칸을 비워 같은 회의록이 두 번 저장되지 않게 한다.

#### Scenario: 정리하기
- **WHEN** 제목 · 시각 · 본문을 채우고 "정리하기" 를 누른다
- **THEN** `POST /api/teams/{id}/meetings` 가 201 을 돌려주고 새 회의록이 목록 맨 위에 추가되며 입력칸이 비워진다

#### Scenario: 정리 중
- **WHEN** 저장 요청을 기다린다
- **THEN** 버튼은 "정리 중..." 이며 비활성이다

#### Scenario: 필수 칸 비움
- **WHEN** 제목이나 회의 시각이나 본문이 비어 있다
- **THEN** 저장되지 않고 `VALIDATION_ERROR` 400 이 돌아온다

### Requirement: 세 항목 구분 규칙
<!-- 근거: C-10 · D-05 · D-06 / meetings.html, detail.html -->
요약은 회의 전체를 3~5줄로 쓰되 없는 사실을 보태지 않아야 한다(MUST). 결정사항은 합의가 끝난 것만 넣고 논의만 한 것은 넣지 않는다. 할 일은 담당자와 기한이 드러난 것만 넣고 담당자가 없으면 "미정" 으로 적는다.

#### Scenario: 결정 없는 회의
- **WHEN** 본문에 합의가 끝난 항목이 없다
- **THEN** 결정사항은 비고, 상세 화면은 "합의가 끝난 항목 없음" 을 보인다

#### Scenario: 담당자와 기한이 드러난 항목이 없음
- **WHEN** 본문에서 담당자나 기한이 드러난 할 일이 없다
- **THEN** 할 일은 비고, 화면은 "담당자와 기한이 드러난 항목 없음" 을 보인다

#### Scenario: 담당자 미정
- **WHEN** 할 일은 있지만 담당자가 말해지지 않았다
- **THEN** 그 할 일의 담당자는 "미정" 으로 저장되고 지어내지 않는다

### Requirement: 회의록 목록
<!-- 근거: C-01 · C-02 / meetings.html -->
목록은 회의 시각 내림차순이고 본문(body)을 싣지 않아야 한다(MUST). 각 카드는 제목 · 시각 · 참석자 · 요약과 결정 수 · 할 일 수 · 완료 수를 보이며, 카드 띠 색은 목록 순서대로 blue · green · orange · purple · red 를 돌려 쓴다.

#### Scenario: 목록 보기
- **WHEN** `GET /api/teams/{id}/meetings` 를 부른다
- **THEN** 200 과 회의록 배열을 받고 각 줄에는 todo_done_count · todo_total_count · decision_count 가 있으며 body 는 없다

#### Scenario: 빈 상태
- **WHEN** 회의록이 한 건도 없다
- **THEN** 200 + 빈 배열이고 화면은 "아직 회의록이 없음" 과 첫 회의를 올리라는 안내를 보인다

### Requirement: 검색과 기간
<!-- 근거: C-03 · C-04 / meetings.html -->
검색은 `?q=` 로 제목과 참석자만 대상으로 하며 본문은 대상이 아니다(MUST). 기간은 `?from=` 과 `?to=` 의 ISO 날짜이다. 결과가 없어도 404 가 아니라 200 + 빈 배열이다.

#### Scenario: 제목으로 검색
- **WHEN** `?q=배포` 로 검색한다
- **THEN** 제목이나 참석자에 "배포" 가 있는 회의록만 돌아온다

#### Scenario: 검색 0건
- **WHEN** 일치하는 것이 없다
- **THEN** 200 + 빈 배열이고 화면은 "검색 결과 없음" 과 "검색어를 지우면 전체 목록으로 돌아감" 을 보인다

### Requirement: 회의록 상세
<!-- 근거: D-01 · D-07 · D-13 / detail.html -->
상세는 요약 · 결정사항 · 할 일 세 칸을 먼저 보이고 받아쓴 본문은 접어 둬야 한다(SHALL). 본문은 단건 조회에만 실린다. 결정사항은 줄 단위로 끊어 번호를 붙인다.

#### Scenario: 기본 보기
- **WHEN** `GET /api/meetings/{id}` 로 연다
- **THEN** 200 이고 세 칸이 보이며 본문은 접혀 있고 "펼치기" 로 연다

#### Scenario: 없는 회의록
- **WHEN** 없는 id 를 연다
- **THEN** 404 `MEETING_NOT_FOUND` 를 받고 목록 화면으로 돌려보낸다

### Requirement: 회의록 수정
<!-- 근거: D-02 / detail.html, meetings.html -->
회의록 수정은 올린 사람과 팀 owner 만 할 수 있어야 한다(SHALL). 수정 상태는 제목 · 회의 시각 · 참석자 · 본문을 입력칸으로 열고 저장 · 취소 버튼을 둔다. 본문을 고쳐도 받아쓰기와 요약은 다시 하지 않고 뽑아 둔 세 항목은 그대로 둔다.

#### Scenario: 수정 저장
- **WHEN** 올린 사람이 "수정" 을 눌러 네 칸을 고치고 저장한다
- **THEN** `PUT /api/meetings/{id}` 가 200 을 돌려주고 요약 · 결정사항 · 할 일은 바뀌지 않는다

#### Scenario: 권한 없음
- **WHEN** 올린 사람도 owner 도 아닌 member 가 상세를 연다
- **THEN** 응답의 `can_edit` 이 false 이고 "수정" · "삭제" 는 흐리며 눌러도 동작하지 않는다. 서버는 `FORBIDDEN` 403 으로 막는다

### Requirement: 회의록 삭제
<!-- 근거: D-08 / detail.html -->
삭제 전에는 딸린 할 일도 함께 사라진다고 먼저 알려야 한다(MUST). 삭제는 올린 사람과 owner 만 할 수 있다.

#### Scenario: 삭제 확인
- **WHEN** "삭제" 를 누른다
- **THEN** "이 회의록을 삭제" 와 "딸린 할 일도 함께 사라짐. 되돌릴 수 없음" 이 보이고 "취소" 와 "삭제" 를 고른다

#### Scenario: 삭제 실행
- **WHEN** 확인에서 "삭제" 를 누른다
- **THEN** `DELETE /api/meetings/{id}` 가 204 를 돌려주고 딸린 할 일과 댓글도 사라진다
